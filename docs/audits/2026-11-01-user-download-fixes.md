# 用户下载问题修复与实测报告

日期：2026-11-01。基线：0.10.12。本轮针对“下载进度预览未出现、抖音插件按钮异常、指定分享链接解析失败”进行检查和修复，不代表此前所有平台、安装器生命周期验收已经完成。

## 1. 结论

已修复悬浮条第一次点击被悬停展开抵消、扩展按钮反馈后失去底色、右键下载菜单报错、抖音当前作品识别不准确，以及音轨信息未知时把成功解析表现成错误的问题。另补上抖音页面直接提交时的媒体分析保护。后端解析同时增加作品 ID 核对，防止选择页面中的推荐作品。

用户提供的短链 `https://v.douyin.com/ZUl9gxD5v6s/` 已通过真实生产 Manager 完整下载和全片解码验证。Windows 原生调试窗口已实际显示真实任务的进度、速度、三条任务详情，取消置顶和暂停均实测生效。

## 2. 问题、原因与处理

| 问题 | 检查证据 | 修改结果 |
| --- | --- | --- |
| 悬浮条首次点击后仍看不到详情 | Windows 实机第一次点击未展开，第二次才展开；DOM 回归在原代码稳定失败 | 悬停或聚焦先置为展开后，点击原本会再执行折叠；改为点击幂等展开，并取消待执行的折叠计时。移出和 Esc 仍可收起 |
| 用户反馈完全没有进度窗口 | 安装版确为 0.10.12，且已包含浮窗命令；真实设置未关闭浮窗；源代码事件类型和后台创建线程正常 | 没有证据把问题归为旧版未安装。实机慢任务已创建原生透明浮条。快速任务可能在首次 250 ms 合并更新或 WebView 创建前结束，此边界仍存在 |
| 扩展按钮下载后变得难以辨认 | 反馈计时结束将内联背景、文字色、阴影清空，而原基础外观也仅来自内联样式 | 恢复明确的基础底色、文字色及阴影；页面 DOM 更新不再立即覆盖反馈状态 |
| 右键“下载当前媒体 / 16 / 32 连接”失败 | 菜单函数引用了其他函数局部作用域中的 `sendToDesktop` | 显式传入发送回调，覆盖右键菜单及连接数回归 |
| 抖音切换后下载旧视频、推荐作品或错误作品 | 原逻辑可能使用全页推荐链接、旧嗅探缓存、过期 `currentSrc`、作者数据 ID | 拆出小型当前媒体识别模块，优先当前作品和播放器所属卡片，忽略外层作者 ID、旧缓存和推荐链接；图文不误发成背景音频 |
| 推荐流无法识别作品时入口消失 | blob 播放器尚未暴露作品 ID 时没有可发送地址 | 保留按钮并提示打开该作品的分享链接或详情页，不发送首页作为作品 |
| 粘贴抖音链接直接点“开始下载”生成失败项 | 对用户现有失败记录进行最小只读检查：来源 desktop、HTTP 任务、未附媒体选择、总长度 0；前端在尚未分析时直接调用普通任务添加 | 同步识别抖音短链与具体作品页，先分析并进入格式选择，阻止创建裸 HTTP 页面任务；不依赖异步平台识别的完成时机，普通文件/CDN 直链仍正常下载。批量混入抖音作品时明确要求逐条分析 |
| 抖音已找到原片却显示分析错误 | 实机解析已返回正确标题与约 51.5 MiB 原片，但音轨信息未知，默认格式选择抛错 | 分离初始格式选择与严格自动选择：显示“已找到原片，来源未提供音轨信息，请选择原片后下载”；不自动勾选，也不宣称未知音轨一定有声 |
| 页面 SSR 元数据可能属于其他作品 | 原解析拿到第一个带 ID 和媒体信息的对象即返回 | 三处生产解析入口按请求作品 ID 过滤；找不到原作品则继续失败回退，不接受其他作品 |

## 3. 指定抖音样本的真实下载

- 下载格式：明确手选来源返回的 `play-0` 原片；音轨信息在探测阶段保持未知，最终文件经 FFprobe 确认。
- 完整文件：53,972,201 字节，视频 H264，1920×1080，512.066667 秒；音频 AAC，512.047007 秒。
- 完整下载耗时：63.707 秒；全片 FFmpeg 解码通过。
- SHA-256：`94a44ab072e4b2d2093f6c7c8637030e5ca7577f35b184f2ac3571e640a82ce2`。
- SSR 修改前、后下载的文件 SHA-256 相同。

实测还在原生新建任务窗口粘贴了用户整段分享文本：识别为一个抖音链接，真实解析返回对应作品标题和原片候选。本站返回原片并不等于已声明音轨信息，因此仍需用户手动选择该候选。

本轮未复现底层对该短链持续解析失败，不能把此次成功扩展成“所有抖音作品、登录状态、地区和网络环境均可下载”的结论。

现有失败任务并不是带格式选择的媒体任务。修复后应通过“新建任务”重新粘贴分享链接；已有失败记录不会被自动改写为其他任务。裸 HTTP 页面任务若迅速失败，也可能触发前述“结束太快而未显示浮窗”的边界，但本轮没有该旧任务的精确时序，不能断言这就是当时未见窗口的唯一原因。

## 4. Windows 原生悬浮窗实测

先使用独立临时数据目录，避免将验证任务写入用户任务库；桥使用正常模式，没有启用会禁止下载请求的隔离桥守卫。

1. 本地慢速 HTTP 服务提供真实 16 MiB 文件，每任务一个连接；浮窗正常出现，紧凑状态仅显示约 224×28 的透明进度条。
2. 原代码首次点击后详情折回，修复并刷新调试界面后，单击可靠展开。
3. 四个真实任务时，紧凑条显示任务数量，详情默认显示三条；队列中存在未知长度时显示未知进度，没有编造百分比。
4. 取消置顶后，按钮反馈及独立数据库中的 `progress_window_always_on_top=false` 均得到确认。
5. 从悬浮窗暂停最后一个活动下载后，主窗口实际显示“已暂停”，悬浮窗自动隐藏。
6. 四个本地任务完成，其中首个完整文件为 16,777,216 字节，SHA-256 与服务源一致：`341aacac661ccb210720bedaa9ead5d668fe5ea41a73532fc147c71e34040df1`。

真实四任务测试过程中三个任务恰好完成，未单独保留原生“六条展开”验收结果；三/六条展开与折叠、长文件名、大量任务、空任务、键盘和错误恢复由独立 React 浏览器行为检查覆盖。原生实测与浏览器模拟结果分开记录。
